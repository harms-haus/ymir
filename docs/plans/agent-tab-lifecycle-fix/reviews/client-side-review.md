## Task 8.2: InitializeResponse ACP event handled in yws-transport.ts

**Status:** PASS

A new handler block was added to `handleAcpPayload()` in `yws-transport.ts` (line ~464):

```typescript
if (payload.eventType === 'InitializeResponse') {
  const agentTabId = envelopeAgentTabId ?? (data as any)?.agentTabId;
  if (agentTabId && acpSessionManager.hasController(agentTabId)) {
    const capabilities = (data as any)?.capabilities;
    acpSessionManager.handleInitializeResponse(agentTabId, capabilities);
  }
}
```

The `AcpSessionManagerApi` interface was extended with `handleInitializeResponse()` and `getCapabilities()` methods, both implemented in `AcpSessionManagerImpl`. Routing logic is correct: uses `envelopeAgentTabId` first, falls back to `data.agentTabId`, and guards with `hasController()` before calling.

## Task 8.4: AgentPane sends AgentResume for sessions with acpSessionId

**Status:** PASS

In `AgentPane.tsx`, within the tab-syncing `useEffect`, when a session has an `acpSessionId` (indicating a resumed tab):

1. Adds the session ID to `spawningSessionsRef` (for the spawning UI state)
2. Constructs an `AgentResume` message with `type: 'AgentResume'`, `worktreeId`, and `agentTabId`
3. Sends it via `client.send(resumeMessage)`

The `AgentResume` interface was added to `types/protocol.ts` and included in the `ClientMessage` union.

```typescript
if (session.acpSessionId) {
  spawningSessionsRef.current.add(session.id);
  const resumeMessage: AgentResume = {
    type: 'AgentResume',
    worktreeId,
    agentTabId,
  };
  client.send(resumeMessage);
}
```

## Task 8.5: "Agent is spawning" UI state

**Status:** PASS

Implemented through multiple coordinated changes:

1. **`isSessionSpawning()` helper** (AgentPane.tsx): Returns true if session status is `'spawning'` OR if the session ID is tracked in `spawningSessionsRef`.

2. **`spawningSessionsRef`** (AgentPane.tsx): A `useRef<Set<string>>` that tracks which sessions are in the spawning phase. Added to when resuming tabs, cleared when `AgentStatusUpdate` arrives with status `'idle'`, `'working'`, or `'waiting'`.

3. **AgentStatusUpdate listener** (AgentPane.tsx): A `useEffect` subscribes to `AgentStatusUpdate` messages and removes session IDs from `spawningSessionsRef` when the agent transitions out of the spawning phase.

4. **Conditional rendering** (AgentPane.tsx): The `AcpChat` component is only rendered when `!isSessionSpawning()`. When spawning, a spinner and "Agent is spawning..." text is shown.

5. **Type updates:**
   - `AgentStatus` in `types/protocol.ts`: `'spawning'` added to the union
   - `AgentStatus` in `types/generated/AgentStatus.ts`: `'spawning'` added
   - `StatusDotStatus` in `useAgentStatus.ts`: `'spawning'` added
   - `mapAgentStatusToStatusDot()`: maps `'spawning'` → `'spawning'`
   - `useWorkspaceAgentStatusSummary()`: return type and initial state include `spawning: 0`

## Task 8.6: yws-transport handles acpSessionId and processId in AgentStatusUpdate

**Status:** PASS (with note)

The generated types were updated:

- **`AgentStatusUpdate`**: Now includes `acpSessionId: string | null` and `processId: number | null`
- **`AgentSessionData`**: Now includes `processId: number | null`

The store (`store.ts`, not in this diff) already handles `acpSessionId` in the `AgentStatusUpdate` path:
- Uses it for deduplication (finds existing session by `acpSessionId` to avoid creating duplicates)
- Passes it to `addAgentSession()` when creating a new session

**Note:** `processId` is present in the updated types but is not currently stored client-side in the `AgentSession` interface or the store. This appears intentional -- `processId` is primarily a server-side concern for process lifecycle management. The client receives it in the message but doesn't need to persist it for UI purposes. If future features need it on the client, the `AgentSession` interface and store would need updating.
