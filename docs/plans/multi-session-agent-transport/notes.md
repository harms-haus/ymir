## Terminology (User Clarified)

| Term | Description | Generated By |
|------|-------------|--------------|
| `agent_tab_id` | Stable key for an agent tab. Server-generated. Client uses it to look up thread_id and render UI. | Server |
| `process_id` | Ephemeral, assigned when agent process spawns, changes on restart | Server |
| `thread_id` | = `acpSessionId`. ACP conversation identifier. May be undefined initially (retrieved from agent after startup). Can be specified to resume a previous conversation. User can change it. | ACP Agent (via SessionInit) |

## Architecture Rules (User Clarified)

1. **1:1 tab-to-process mapping** — each agent tab has its own dedicated agent process on the server
2. **agent_tab_id is SERVER-GENERATED** — client just requests by worktreeId, server creates the tab record and returns agent_tab_id
3. **thread_id is ephemeral** — user can switch threads; server loads correct thread in the ACP process
4. **Shared thread_id is CLIENT-SIDE only** — multiple UI tabs read from the same accumulated state, but each has its own process
5. **acp-chat-core** accumulates state keyed by thread_id — NO changes needed
6. **acp-ws-bridge** passes thread_id through — minimal changes
7. **Client UI** maps agent_tab_id -> thread_id to look up thread state from acp-chat-core

## agent_tab_id Lifecycle (Corrected)

1. Client sends request to create agent tab (AgentSpawn by worktreeId)
2. Server generates `agent_tab_id` (UUID), creates tab record, links to worktree
3. Server spawns agent process for that tab
4. Agent process sends `SessionInit` with `acpSessionId` (thread_id)
5. Server links `agent_tab_id` -> `thread_id`
6. Client receives `agent_tab_id`, uses it to look up `thread_id` from store, renders the thread
